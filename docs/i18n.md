# Internationalization (i18n)

The Windows client has **three i18n catalogs**, because its user-facing text is
produced in three places:

| Catalog | Surface | Owner | Mechanism |
|---|---|---|---|
| `ui-locale-bundles` (vendored) | Renderer UI (all `@phlix/ui` screens, shell, palette, player…) | `phlix-ui` (SSOT) | config-time override seam: `createPhlixApp({ messages })` fed SHA-pinned vendored bundles |
| `windows-own` (renderer) | Top-bar nav labels — `MenuItem.label` strings this client *supplies to* the ui shell | this repo | local catalog + `tWin()` in `src/renderer/i18n/windows-own/` |
| `main` | Main-process chrome (tray, app menu, thumbar tooltips, updater notifications, About dialog) | this repo | local catalog + `t()` in `src/main/i18n/` |

## Locale matrix

Six locales ship alongside English: `es`, `fr`, `de`, `it`, `pt_BR`, `ja`.
One tag resolution law drives all three catalogs: trim → lowercase → primary
subtag (`-`/`_` split), with the estate region rule `pt* → pt_BR` (the estate's
single Portuguese catalog). Unregistered tags fall back to `en` silently —
untranslated desktops get working English, never an error.

| Tag (and any region variant) | ui seam bundle | windows-own nav | main chrome |
|---|---|---|---|
| `en` | *(omitted — ui renders its own defaults byte-identically)* | `windows-own/en.ts` | `main/i18n/en.ts` |
| `es` | vendored `ES_MESSAGES` | `windows-own/es.ts` | `main/i18n/locales/es.ts` |
| `fr` | vendored `FR_MESSAGES` | `windows-own/fr.ts` | `main/i18n/locales/fr.ts` |
| `de` | vendored `DE_MESSAGES` | `windows-own/de.ts` | `main/i18n/locales/de.ts` |
| `it` | vendored `IT_MESSAGES` | `windows-own/it.ts` | `main/i18n/locales/it.ts` |
| `pt`, `pt-BR`, `pt_BR`, `pt-PT` | vendored `PT_BR_MESSAGES` | `windows-own/pt_BR.ts` | `main/i18n/locales/pt_BR.ts` |
| `ja` | vendored `JA_MESSAGES` | `windows-own/ja.ts` | `main/i18n/locales/ja.ts` |

Selection: two chains, one knob each. The renderer (the vendored `@phlix/ui`
bundles and the windows-own catalogs) resolves `VITE_PHLIX_LOCALE` (build-time
env; accepts any tag above) → `navigator.language` → `en`
(`src/renderer/i18n/index.ts:109`). The main process has **no env read**: its
tag resolves `app.getLocale()` (pinned once at `whenReady` via
`setMainLocale(mainLocale)` near the top of the ready handler in
`src/main/index.ts` — symbol cite per the coordinates-rot law) → `en`.

## 2. Windows-own renderer catalog — nav, boot-failure, deeplink and overlay labels (`tWin`)

`buildMenu()` in `src/renderer/main.ts` hands `createPhlixApp` raw
`MenuItem.label` strings (My Servers, Federation, Shares, Shared with Me,
Invite Links, Watch History, Explore, Recommendations, Admin, Browse, Music,
Books, Audiobooks, Photos, Search, Settings, SyncPlay). The ui seam localizes ui-rendered
text but **never these**, so they live in
`src/renderer/i18n/windows-own/` — a typed catalog (41 keys by the counting rule below:
nav 17 + boot-failure screen 9 + deeplink notices 3 + player overlay 12; `WIN_EN` is the SSOT; locales
`satisfies WindowOwnCatalog`), `setWindowLocale(tag)` pinned at boot before the
menu assembles, `tWin(key)` fail-loud on unknown keys.

**Counting rule** (defines both client-catalog counts in this doc): one key = one
flattened `group.key` leaf of the English SSOT object — `WIN_EN` here, `en` in
`src/main/i18n/en.ts` below. Every string-valued entry at the second object level counts
exactly once, no matter how many lines its value spans; comment lines, group headers, and
the six non-English locale mirrors never change the number (each mirror `satisfies` the
SSOT's shape, so one SSOT count is the count for all seven locales).

M-WINDOWS-11: the player overlay (SleepTimer + PiPButton) used to ship
hardcoded English. Its labels now read the same catalog. The overlay is loaded
by `main.ts` as a **dynamic import** — same realm, same windows-own module
instance (the built output confirms it: catalog strings sit in the main chunk)
— so the single boot-time `setWindowLocale()` pin governs shell and overlay
alike, and it precedes the import (`overlayI18n.test.ts` pins that ordering
and forbids a second pin in `overlay.tsx`).

English values are byte-identical to the pre-i18n hardcoded literals —
`tests/unit/i18nSeamWiring.test.ts` pins them through `buildMenu()` itself,
`tests/unit/overlayI18n.test.ts` pins the overlay group (catalog parity,
zero-literal component scans, and the overlay.tsx locale pin). The sole
exception is `syncplay` — born catalog-first with the M-WINDOWS-04 rider leg 2
(tag-wave C4 v0.99.12 re-pin, 2026-11-02), value the estate brand term
`SyncPlay` (ja composes it CJK-side as `SyncPlay同期視聴`, mirroring the ui ja
bundle's brand treatment and satisfying the windows-own 100%-CJK law).

## 3. Main process — local catalog + `t()`

Main-process strings never touch the Vue app, so they live in
`src/main/i18n/en.ts` (54 keys by the counting rule above — nine groups: tray 7 · menu 13 ·
thumbar 4 · updater 8 · about 3 · boot 3 · deeplink 6 · crash 4 · net 6) with locales under
`src/main/i18n/locales/`,
resolved by the pure, electron-free `t()` in `src/main/i18n/index.ts`.

**Ready-ordering:** `app.getLocale()` requires the Electron `ready` event. The
locale is pinned **once** at the top of the `app.whenReady()` callback (before
`createWindow`/`createMenu`/`createTray`), and every string builder runs after
that point. `buildPlaybackMenuTemplate()` is a function (not a module-scope
const) precisely so its labels are evaluated post-ready. Role-based menu items
(`role: 'quit'`, `role: 'reload'`, …) intentionally keep no label — Electron
renders roles with native, already-localized strings.

`tests/unit/mainI18n.test.ts` pins every extracted EN value against the literal
that was hardcoded before the extraction; the ×6-locale laws live in
`tests/unit/i18nLocales.test.ts`.

## Adding a 7th locale (e.g. `ko`) — three halves, one recipe

1. **ui bundle (SSOT-first):** the bundle must exist in phlix-ui
   (`src/i18n/locales/ko.ts` + registry). Advance `SOURCE_REF` in
   `scripts/sync-ui-locale-bundles.mjs` to the commit containing it AND advance
   the npm pin (`package.json`/lock) to a released `@phlix/ui` carrying the same
   catalog — since v0.99.5 the two pins stay in lockstep, so a vendor ahead of
   the installed catalog is a red set-equality law by design, resolved by
   moving both pins, never by loosening the law. Then register the bundle: one
   `registerLocaleOverrides` loop already covers it via `LOCALE_MESSAGES`; add
   `'ko'` to `SUPPORTED_LOCALES` in `src/renderer/i18n/index.ts`.
2. **windows-own nav:** author `src/renderer/i18n/windows-own/ko.ts`
   (`satisfies WindowOwnCatalog`) + one `catalogs` entry in
   `windows-own/index.ts`.
3. **main chrome:** author `src/main/i18n/locales/ko.ts`
   (`satisfies MainCatalog`) + one `catalogs` entry in `src/main/i18n/index.ts`.

Then extend the tables in `tests/unit/i18nLocales.test.ts` (key-set identity,
placeholder parity, EN-leak allow-lists both directions, diacritics/CJK sanity,
resolution matrix) and the matrix above. Missing catalog keys are compile
errors; missing registry entries are test failures.

## What is NOT localized

- **Electron role-based menu items** (`role: 'quit'`, `role: 'reload'`, window
  controls…) — Electron renders native labels, already localized by the OS.
- **Log lines** (`log.info` etc.) — developer-facing, intentionally English.
- **IPC notification payloads** (`notification:show`) — strings come from the
  renderer (i.e. already inside ui's seam or page-local copy upstream).
- **Deep-link rejection** — there is no dialog to translate:
  `handleDeepLinkUrl` (`src/main/index.ts:133`) silently drops a URL whose path
  cannot be parsed (`if (!path) return;`); the only other leg is a `log.warn`
  for a missing window. (An earlier revision of this doc referenced a
  `showErrorDialog` that does not exist — corrected.)
